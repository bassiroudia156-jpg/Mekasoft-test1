## Pricing simplified: Business tier retired, merged into Pro/"Premium" (2026-08-20)

Per user decision, after living as a real 3-tier system (Gratuit/Pro/Business — see the 2026-08-18 entry below): the BUSINESS plan is **retired**. All of its advantages (up to 5 users with roles, monthly report PDF, CSV export) now ship on **PRO**, which is displayed as **"Premium"** everywhere (the internal/DB/Stripe identifier stays `'PRO'` — see `lib/server/plans/limits.ts`'s header comment for why). FREE is unchanged. Price kept at the old Pro price, 9 900 FCFA/mois (user's explicit choice) — the existing `STRIPE_PRICE_ID_PRO` Stripe Price object needed no dashboard change.

- `lib/server/plans/limits.ts` — `PLANS` is now `['FREE', 'PRO']`; `PLAN_LIMITS.PRO` gained `maxUsers: 5` and all `features: true`; `PLAN_LIMITS.BUSINESS` removed; `PLAN_PRICING.PRO.label` is now `'Premium'`.
- Every consumer keyed on the now-removed `'BUSINESS'` literal was found via `PayablePlan = Exclude<Plan, 'FREE'>` narrowing to just `'PRO'` and re-running `tsc --noEmit` until clean, then a text sweep (`grep -ri BUSINESS`) for copy/comments TS wouldn't catch.
- Two real bugs caught by that sweep (not just cosmetic): `components/dashboard/ExportMenu.tsx` was still gating on `plan === 'BUSINESS'` (would have shown the Premium org's own upsell copy to itself, forever hiding its export/report links); `app/dashboard/page.tsx`'s `showUpgrade` prop was `orgPlan !== 'BUSINESS'` (always true post-retirement, so the "Upgrader" pill would show to Premium subscribers too) — fixed to `orgPlan === 'FREE'`. Also `lib/server/subscriptions/types.ts`'s `isPayablePlan()` still accepted `'BUSINESS'` as payable — fixed to `=== 'PRO'` only, so a stale legacy row can't slip through as payable.
- UI: `app/page.tsx` (landing `#tarifs`), `app/subscriptions/plans/page.tsx`, `app/profile/page.tsx`, `components/subscriptions/UpgradeSubscriptionModal.tsx` collapsed from 3-card/plan-picker layouts to 2-card/single-plan-summary; `app/subscriptions/checkout/page.tsx` dropped its now-dead `?plan=PRO|BUSINESS` query param entirely.
- No real customer was ever on BUSINESS (verified against the live DB before implementing) — code-only change, no data migration needed.

## Search bar audit (2026-08-18)

User asked for a full audit of every search bar — "je veux que ça marche pour tout par exemple nom de client, véhicules" (client name, vehicles, etc. should all work). Inventoried all 9 real search inputs in the app (list pages: clients/vehicles/interventions/invoices/payments; creation-flow client/invoice comboboxes: vehicles-new/invoices-new/payments-new/interventions-new; the dashboard's client/vehicle filter comboboxes) and checked each against its backend route. Found two real, confirmed bugs — one exactly matching the user's own example.

### Bug 1 — `/vehicles` never searched by owner name
The page shows a "Propriétaire" column but `GET /api/vehicles`'s search only matched `brand`/`model`/`registration` — a user who remembered the client's name but not the plate had no way to find their vehicle from this page (the literal case the user described). Placeholder updated: "Chercher marque, immatriculation…" → "…, propriétaire…".

### Bug 2 — search silently vanished on page 2+ of results (all 5 list routes)
All 5 list routes (`clients`, `vehicles`, `interventions`, `invoices`, `payments`) build their Prisma `where` by spreading two conditional fragments into the same object: `...(q ? { OR: [...search conditions] } : {})` and `...cursorWhere(cursor)` (cursor pagination is itself implemented as `{ OR: [{createdAt: lt}, {createdAt: eq, id: lt}] }`). Both fragments use the key `OR` — object spread means the second one silently **overwrites** the first. Result: searching normally (page 1, no cursor) worked fine, but paginating past the first page **while a search query was active** silently dropped the search filter entirely and returned the next page of the *unfiltered* list instead. This is a correctness bug that would only surface with enough matching rows to paginate — plausible in any org with real usage, easy to miss in day-to-day testing with few records. Fixed identically across all 5 routes: both conditional fragments now nest inside an `AND` array instead of colliding as sibling top-level keys, so either, both, or neither can be present without stepping on each other.

### Also found, same audit: every list-page search box fired on every keystroke, unguarded
None of the 5 main list pages' free-text search inputs were debounced — every character typed fired an immediate request. Two of them (`clients`, `interventions`) already used an inline-effect-with-`cancelled`-flag pattern that happened to make them race-safe (a stale response is correctly ignored), just wasteful. The other three (`vehicles`, `invoices`, `payments`) used a named `load()` function with **no** race guard at all — a slower response to an earlier keystroke could resolve after a faster response to a later keystroke and silently leave the list showing results that don't match what's currently typed in the box. Fixed uniformly: `q` now debounces into a `qDebounced` state (300ms while typing, instant when clearing the box) that the fetch effect actually depends on, cutting request volume from one-per-keystroke to one-per-pause; the 3 `load()`-based pages additionally gained a `loadSeq` ref (increment-and-compare pattern) so even an out-of-order response can never overwrite newer state, closing the race regardless of network timing. Status-filter button clicks stayed instant (not debounced) since those aren't a typed field.

Not changed: the SearchSelect-based comboboxes in the 4 creation flows and the dashboard's client/vehicle filters were all already correctly debounced (`setTimeout` + a `cancelled` closure flag) — audited and confirmed clean, no fix needed there.
